# 自动化信息获取方案调研（2026-08 更新）

> 前作：`research/payment-platform-apis.md`（2026-04-23）。
> 本次聚焦一个新痛点：**现有实现依赖手动 CSV 导出 / 第三方 App 截图，无法形成自动化闭环。**
> 结论先行：2026 年这个时间点，「官方账单邮箱推送 + IMAP 全自动解析」已是唯一合规的全自动主路径；
> 「Android 短信/通知转发」负责实时性；「截图 + 多模态模型入库」作为现有截图习惯的升级而非主依赖。

---

## 1. 当前事实盘点

| 渠道 | 个人开放 API | 月度账单发到指定邮箱 | 动账短信 | 本仓库现状 |
|---|---|---|---|---|
| 支付宝 | 开放平台账单接口（需签约资质，见 §3） | ✅ 加密 zip，密码在短信/邮件正文 | ✅ | 已有 openapi client + 邮件 parser |
| 微信支付 | ❌（商户号专用，需营业执照） | ✅ 加密 zip（「用于个人对账」），密码在邮件正文 | ✅ | 仅通知类邮件 parser，无 zip 解析 |
| 商业银行 | ❌（仅企业银企直联） | 多数支持对账单邮件 | ✅ 信息最完整 | CMB/Bankcomm HTML parser |
| 京东/淘宝/拼多多 | ❌ | 订单相关营销/物流邮件可解析 | 经支付宝/微信间接覆盖 | 各有 parser |

关键约束未变：微信、京东、淘宝、拼多多的个人消费数据**没有**公开 API。

## 2. 核心新发现：官方「账单邮件」已构成全自动闭环

2026 年活跃开源项目 [`Guogeda/auto-jizhang`](https://github.com/Guogeda/auto-jizhang)
验证了完整链路（其 README 明言这是"唯一无需爬虫、合规稳定的自动化获取方式"）：

```
在微信/支付宝「账单 → 导出」中把月度账单寄送到专用邮箱
   ↓
IMAP 定时拉取（本仓库已有 EmailClient）
   ↓
自动下载加密 zip 附件，密码从邮件正文/环境变量获取
   ↓
解压出官方格式 CSV → 逐条规范化为 RawTransaction（复用去重/分类管线）
```

- 触发成本：每月在手机上约 1 分钟的导出操作；服务端零人工。
- 本仓库缺口很小：缺「带附件加密 zip 的邮件 → 官方账单 CSV 解析器」，IMAP/导入/去重/月汇总基建全部现成。
- 支付宝另有「开具交易流水证明」邮件通道，格式同为 zip+密码，可共用同一 parser 家族。

## 3. 支付宝开放平台 API：保留但降级为可选

- `alipay.data.dataservice.bill.downloadurl.query` 的 client 本仓库已实现。
- ⚠️ 4 月报告中"个人开发者可用"的判断需要在开放平台控制台实际验证：该产品通常要求企业/个体工商户签约「账单查询」权限。
- 处理策略：有资质就接入定时任务；没有也不阻塞——§2 的邮件路径输出的是同样的官方数据。

## 4. Android 短信/通知转发：实时性补齐，成本极低

[`pppscn/SmsForwarder`](https://github.com/pppscn/SmsForwarder)（27.7k★，BSD-2，持续维护，适配 Android 4.4–13）：

- 监控短信/来电/**APP 通知**，按规则（发件人、关键字如"支出/入账/余额"）转发到 **webhook**、邮箱、Server酱等。
- 推荐部署：一台插 SIM 的安卓备用机跑 SmsForwarder，把银行动账短信 POST 到本仓库**待新增**的 `/ingest/webhook` 端点（token 鉴权 + 幂等去重），解析金额/商户/卡尾号后进标准入库管线。
- 收益：银行消费秒级入账，且不依赖任何银行 API；短信模板固定，正则解析可靠性高。
- APP 通知监听可捕获"支付成功"类通知，但内容比动账短信贫瘠，作为补充规则开启即可。

## 5. 截图习惯升级：多模态模型入库（半自动）

现状"第三方 App 截图"可以原样升级为结构化入账管道：

```
截图（手机相册/分享面板） → PTS 新增图片上传端点
   → 视觉模型抽取 {日期, 金额, 方向, 商户} （复用已有 litellm 依赖）
   → 输出待确认列表 → 人工一键确认后走 RawTransaction 标准入库
```

- 可行性已被同类项目验证：[`hnkjdaxzzq/autocoin`](https://github.com/hnkjdaxzzq/autocoin)（Python/FastAPI，2026-03 更新）同时支持支付宝/微信账单导入和多模态 LLM 识别收据照片/截图自动入账。
- 基础设施已就绪：本仓库 pyproject 已含 `litellm>=1.43.0` extra，`classifiers.py` 的 `LiteLLMClassifier` 已打通 LLM 调用与降级模式；litellm 的 vision message 格式可直接复用同一套 settings/model 配置。
- 成本：每张截图几分钱以内（Qwen-VL/GLM-4V/GPT-4o-mini 量级）。
- 定位：**确认式入库**，不是无人值守自动化——非结构化来源必须保留人工核对。

## 6. 其他被评估但暂不推荐的方向

| 方向 | 结论 |
|---|---|
| 自研 Android 无障碍记账 App（钱迹模式） | 工程量与维护成本远超收益；改用钱迹等 App 的账单导出 CSV 走既有导入管线即可"白嫖"其无障碍能力 |
| iOS 快捷指令截获支付事件 | 平台不允许；iOS 主流做法仍是导出到邮箱 |
| Computer-use 浏览器代理驱动导出（ChatGPT Agent / Claude computer use / Gemini computer use） | Operator 已于 2025-08-31 下线由 ChatGPT Agent 取代；商用成熟度提升，但登录网银/支付平台必然撞上风控、验证码与代理安全策略（拒操作支付页）→ 仅列为实验观察项 |
| 云闪付/H5 抓取、网页模拟登录 | 反爬与账号风控风险高，维持既有"不做爬虫"的项目边界 |

## 7. 推荐落地优先级

**P0 —— 官方账单邮件全自动入库（最高性价比）**
1. 扩展 `EmailImportService`：处理带 zip 附件的账单邮件（zip 密码走环境变量 `PTS_BILL_ZIP_PASSWORD_*`）。
2. 新增 `parsers/wechat_bill_zip.py` 与增强 `alipay.py`：解析官方账单 CSV 字段（交易单号/时间/对方/金额/收支），external_id 天然幂等防重。
3. 映射表：`server/importers/email/client.py`（取附件）、`service.py`（路由）、新增 parser、`tests/unit/` 用例。

**P1 —— 动账短信实时入账**
1. 新增 `POST /ingest/webhook` 端点（X-API-Key 复用鉴权 + raw body 存档 + 幂等）。
2. 新增 SMS 文本 parser（银行动账模板正则），接入 ImportResult 管线。
3. 手机侧配置一次 SmsForwarder 即完成交付。

**P2 —— 截图视觉入库**
1. 新增 `POST /bills/screenshots` 上传端点与 Finance tab「导入选图」入口。
2. 复用 litellm 配置实现 vision 抽取器，产出**待确认**草稿而非直接入账。

**实验观察**：browser agent 自动化导出；支付宝开放平台资质核验结果。

## 8. 风险与边界重申

- 各官方入口（导出按钮文案、zip 格式字段）可能随版本调整 → parser 必须带容错与告警，失败落盘原始数据供人工排查。
- 加密 zip 密码、webhook token 属敏感信息 → 一律环境变量，不入库不入 git。
- 所有自动化路径都必须保持文档中的诚实边界：承诺程度与实际实现一致（沿用 requirements.md §2.4 的约定）。

## 9. 补充专题：电商 APP（淘宝/京东/拼多多）与全渠道覆盖矩阵

> 用户追问：这几类 APP 不支持邮件发送账单，截图又太麻烦，有没有更好的方式？
> 核心架构结论：**不要试图从电商平台本身拿账单数据。**
> 把需求拆成两层分别解决，覆盖率立刻从 0 变成 ~100%：

### 9.1 两层拆解

| 层 | 回答的问题 | 数据来源 | 自动化程度 |
|---|---|---|---|
| **金额层（对账）** | 这笔钱何时花的、花在哪、多少 | 支付宝/微信支付账单 + 银行动账短信 | 全自动（P0/P1 方案已覆盖） |
| **明细层（买了什么）** | 具体商品/订单是什么 | 电子发票邮件 PDF / 订单页自动化导出 / 截图 VLM | 半自动~全自动 |

电商 C 端订单几乎全部经支付宝或微信支付完成，而支付宝月度账单 ZIP（P0 邮件通道）里的交易对方字段会显示平台商户标识（如拼多多显示为"XX信息技术有限公司（拼多多平台商户）"、京东为"京东商城商家"类名称）。**所以只做 P0/P1，所有电商消费就已经金额级自动入库了**——这与旧报告 §7.2 的判断一致，且如今由加密 zip 通道自动化交付。

### 9.2 明细层四个通道对比（2026-08 现状）

| 通道 | 原理 | 可靠性 | 维护成本 | 结论 |
|---|---|---|---|---|
| **A. 电子发票邮件 PDF**（京东 ✓ 最好；天猫部分 ✓；普通淘宝 C 店 ✗；拼多多基本 ✗） | 结算时选电子发票发到专用邮箱 → IMAP 收附件 → pdfplumber 解析行项目 | 高（官方直投、格式规范、天然幂等） | 低 | **首选，并入 P0** |
| **B. Android 无障碍脚本导出订单页** | Hamibot（商业 SaaS，3.1k★）/ AutoJs6（6.3k★，2026-03 仍在更新）/ EasyClick（支持鸿蒙+iOS）驱动真机打开"我的订单"逐条读取 → POST webhook | 中（受 UI 改版影响） | 中（脚本需跟进改版） | 备选，P3 |
| **C. 云手机 + GUI Agent** | Mobile-Agent-v3.5 / GUI-Owl（阿里通义，9.1k★）已上线**阿里云无影云手机商用**；无需自备机 | 中（Agent 准确率未达人类水平；登录仍涉账号风控） | 高 | 实验观察 |
| **D. 截图 + VLM**（原 P2） | 相册截图上传 → 视觉模型抽取 | 高（有人工确认） | 低 | 兜底保留 |

要点补充：

- **A 通道基建已齐**：`pyproject.toml [server]` extra 早已包含 `pdfplumber`、`openpyxl`、`bs4/lxml`——PDF/Excel/HTML 三种附件格式解析的能力当初就已预留。只需新增 `parsers/invoice_pdf.py`：识别数电票/普票 PDF 中的日期、行项目、价税合计、销售方，映射为 RawTransaction（external_id 用发票号码，天然防重）。
- **B 通道形态**：Hamibot 提供 REST API 远程派发任务/多设备管理/定时执行，等于"手机侧 RPA 服务端化"；PTS 侧只需复用同一 `/ingest/webhook`。与其自己开发脚本，也可先用 Hamibot 脚本市场现成工具过渡验证链路。
- **C 通道进展**：Mobile-Agent 家族 2026 年发布 v3.5 与 ToolCUA（GUI 工具编排），从"科研 demo"进入"云服务可用"，但仍不适合作为个人记账主依赖——成本高、风控不可控。
- **拼多多没有干净通道**：无 API、基本无发票邮件、账单仅显示平台商户名。现实策略 = 支付账单金额层全覆盖 + 少量大额订单手动截图/D 通道。

### 9.3 全渠道覆盖矩阵（最终状态）

| 渠道 | 金额层来源 | 明细层来源 | 综合覆盖率 |
|---|---|---|---|
| 主流银行 | 动账短信 webhook（P1）+ 月对账单邮件 HTML（已有 parser） | 消费短信备注/交易附言 | ~100% |
| 支付宝 | 月账单加密 zip 邮件（P0）+ 开放平台 API（有资质则接入） | 账单自带商品说明 + 部分发票邮件 | ~95% |
| 微信支付 | 月账单加密 zip 邮件（P0） | 账单自带商户名 | ~90% |
| 淘宝/天猫 | 经支付宝账单间接覆盖 | 天猫电子发票邮件 PDF（A） | 金额 100% / 明细部分 |
| 京东 | 经支付宝/微信/银行卡间接覆盖 | 电子发票邮件 PDF（A，最佳）+ B 兜底 | 金额 100% / 明细 ~85% |
| 拼多多 | 经支付宝/微信间接覆盖 | 仅 D/B 通道 | 金额 100% / 明细按需 |

### 9.4 更新后的行动清单

1. **P0 扩充**：在「账单 zip 邮件解析器」之外，一并实现 `invoice_pdf.py` 发票 PDF 解析器（同一封邮件工作流、同一测试基建，边际成本极低）。
2. **P3（新增）**：写一份 AutoJs6/Hamibot 的示例订单采集脚本规格（目标：京东"我的订单"列表 → JSON → `/ingest/webhook`），作为无障碍通道的最小原型；后续视使用频率决定是否投入维护。
3. **实验区**：注册一个阿里云无影云手机试用 Mobile-Agent-v3.5，实测登录态下"读取订单列表"任务的稳定性，得出第一手 Go/No-Go 数据。
4. 其余沿用上文 P0/P1/P2 与风险边界（§8）不变。
